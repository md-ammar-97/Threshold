# Gold evaluation datasets

This directory holds real, human-authored gold annotations, loaded via
`scripts/load_gold_dataset.py`. It ships empty on purpose.

## Why no gold data ships with this repo

Gold labels exist to check whether the system's own outputs (classifications,
retrieval, generated answers) are correct. If those labels were themselves
generated by an LLM — even a different one, even with a careful prompt — a
systematic model error and the "gold" label checking for it would tend to
share the same blind spot, and the check would validate nothing. Gold data
has to come from a human who actually read the source text and decided what
the correct answer is. Nobody has done that yet for this project, so this
directory stays empty until someone does. `scripts/load_gold_dataset.py`
and `validation/gold_loader.py` are the infrastructure for loading that data
once it exists — not a source of the data itself.

## What the loader does

`load_gold_dataset_from_file()` reads a JSONL file, gets-or-creates an
`evaluation_dataset` row (by `--dataset-version`), and for each line either
creates a new `evaluation_dataset_item` or updates an existing one (matched
by `object_type` + `object_id` within that dataset). It writes the gold
value in two places every time, both required for it to be picked up
correctly:

1. `evaluation_dataset_item.gold_output` — read directly by
   `validation/runners.py`'s `run_evaluation()`, the actual grading
   pipeline.
2. An adjudicated `annotation` row — read by
   `validation/annotations.py::get_gold_output()` and the two-annotator
   audit trail (`ai_evals.md` §7).

These are two separate mechanisms in this codebase; a hand-written script
that only writes one will silently break the other. Load through
`scripts/load_gold_dataset.py`, not by hand.

**Current limitation, so you don't waste time on it:** none of the graders
implemented so far in `validation/graders/` (`citations.py`, `grounding.py`,
`privacy.py`) actually read `gold_output` — they're all deterministic,
rule-based checks against the candidate output alone. `gold_output` is
already threaded through the `EvalGrader.grade()` signature and the
`run_evaluation()` pipeline, ready for a future gold-comparison grader, but
loading a gold file today doesn't yet change what any existing grader run
reports. Also note `run_evaluation()` only has a candidate-output resolver
for `object_type: "generated_answer"` today (`runners.py::_resolve_candidate_output`)
— gold items of any other `object_type` will load and adjudicate correctly,
but a grading run will count them as failed items (`NotImplementedError`,
caught per-item) rather than actually grading them, until a resolver for
that object type is added.

## File format

One JSON object per line (JSONL). Blank lines are skipped.

```json
{"object_type": "generated_answer", "object_id": "<uuid of a real generated_answer row>", "input_snapshot": {"question_text": "What frustrations do users report repeatedly?"}, "gold_output": {"expected_finding_count": 3, "notes": "human-written summary of what a correct answer should cover"}, "metadata": {"annotator": "your name", "annotated_at": "2026-08-01"}, "notes": "optional adjudication note"}
```

| Field | Required | Meaning |
|---|---|---|
| `object_type` | yes | One of `feedback_record`, `research_question`, `theme`, `generated_answer` (`validation/models.py::EvaluationObjectType`). Use `generated_answer` if you want the item to actually participate in a `run_evaluation()` grading run today (see limitation above). |
| `object_id` | yes | UUID of the real, already-persisted row being evaluated (e.g. a `generated_answer.id`). Must reference something that actually exists — the loader does not validate this at load time, but `run_evaluation()` will fail that item at grading time if it doesn't. |
| `input_snapshot` | yes | Immutable snapshot of the test input (dict, may be `{}`). For `generated_answer`, the question text asked is the natural choice. |
| `gold_output` | yes | The human-decided correct answer (dict, may be `{}`). Shape is grader-specific; there's no fixed schema yet since no grader reads it — write whatever a future gold-comparison grader would need (e.g. the set of themes a correct answer should cite). |
| `metadata` | no | Free-form dict stored on the dataset item (e.g. annotator name, date). |
| `notes` | no | Stored on the adjudication `annotation` row. |

## Loading a file

```bash
python scripts/load_gold_dataset.py data/evaluation/my_gold_set.jsonl \
    --dataset-version 2026-08-v1 \
    --dataset-name "Ask-workspace answer quality gold set" \
    --evaluation-type grounding \
    --partition validation
```

`--dataset-version`/`--dataset-name`/`--evaluation-type`/`--partition` are
only used the first time a given `--dataset-version` is loaded (dataset
get-or-create); re-running against the same version updates existing items
in place rather than duplicating them.
