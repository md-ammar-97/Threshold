## 1. Executive Summary

This is an unusually well-engineered system whose **quality architecture substantially exceeds its data reality**. The evidence-integrity machinery — versioned taxonomy, server-assigned citation labels resolved against a same-request evidence package, deterministic scoring, demographic and causal guards, an auditable retrieval funnel — is genuinely strong and, in several places, better than the specification asked for. The documentation is honest to a degree that is rare; `docs/implementationplan.md` explicitly flags its own gaps rather than papering over them.

The problems are concentrated in three places:

1. **Source breadth is a facade.** Seven source types are required. Eight connectors exist as code, but only one (Google Play) has ever produced real data. Five require an `APIFY_TOKEN` that is blank in `.env.example`. Two of the seven required categories — *community forums* and *quick-commerce discussions* — have no purpose-built implementation at all, only a generic single-URL HTTP fetcher with no seed list, no crawler, and no RSS reader.

2. **Two wiring defects break the discovery pipeline end-to-end under default configuration.** Theme clustering reads embeddings from a hardcoded `local` embedding configuration while the default `EMBEDDING_PROVIDER=hosted` writes them under a different one — clustering will find zero vectors and produce zero themes. Separately, research retrieval filters records to the theme-set's `analysis_run`, but the CLI creates classification and clustering under two *different* runs — retrieval returns zero records. Both defects are invisible to the test suite because its fixtures construct a single, correctly-linked run by hand.

3. **Two of the eight research questions are not answerable.** "How do users discover products today?" and "Which user segments are more likely to experiment?" have no taxonomy dimension, despite `docs/context.md` §7.C/§7.D specifying exactly what those dimensions should contain and despite `ThemeType.DISCOVERY_MECHANISM` and `ThemeType.EXPERIMENTATION_SIGNAL` already existing as enum values with nothing that can populate them.

Secondary but material: there is **no insights UI or API surface** (insights are generated and stored but reachable only indirectly through a research answer); **no Celery task exists anywhere**, so the worker container is inert and every pipeline stage is a manual CLI invocation; citations in the Ask workspace are rendered without a click handler, so evidence traceability stops at a hover tooltip; and the evaluation framework grades only its own generated answers against rule-based checks — `data/evaluation/` is empty, there is no gold dataset, and no classification, retrieval, or theme grader exists.

**Readiness: 62%.** The hard parts (grounding architecture, data model, provenance) are done well. The remaining work is breadth, wiring, and two missing taxonomy dimensions — mostly tractable, but the pipeline does not currently run end-to-end on default settings.

### 2.2 Findings

**F-1 — Community forums are not genuinely supported.** `PublicWebConnector` fetches a list of literal URLs supplied by the operator and extracts main-body text. It has no link discovery, no pagination, no thread/comment structure parsing, and no forum-specific adapters. `_urls_from_config` (`public_web.py:55`) simply concatenates `target_identifier` with `configuration["urls"]`. MouthShut, Quora, and PissedConsumer — named explicitly in `docs/problemstatement.md:72` — have no implementation and appear nowhere in the codebase (grep for these terms returns zero hits outside the problem statement). A forum thread would be captured as a single flat `article_passage`, discarding the per-comment structure the whole analysis depends on.

**F-2 — Quick-commerce industry commentary is entirely absent.** `docs/problemstatement.md:73` names Entrackr, Inc42, YourStory, Moneycontrol and recommends "direct HTTP fetching, an RSS reader, or a lightweight web-crawling workflow." Grepping the entire repository for these outlets returns zero matches. There is no RSS module, no scheduled fetch, and no seeded source list. The category is Missing, not Partial.

**F-3 — Product review platforms are represented by the wrong platform.** Product Hunt is a tech-product launch board. For a grocery quick-commerce brand it will yield essentially no relevant discussion. The connector's own docstring concedes it was "added as a clean, official-API alternative to the undocumented forum-scraping approach" (`producthunt.py:3-5`). Amazon, Flipkart, MouthShut, and Trustpilot — where Indian consumers actually review products — are absent.

**F-4 — Facebook cannot do discovery, and the code says so.** `facebook.py:5-13` documents that `apify/facebook-posts-scraper` requires explicit `startUrls` and "has no keyword-search field at all… it cannot search Facebook for what people are saying about a brand." It also flags "real ToS risk — Facebook's scraping terms prohibit this." This connector contributes nothing to the stated research goal and carries legal exposure.

**F-5 — Cost controls are declared but never enforced.** `MAX_COLLECTION_COST_USD`, `DEFAULT_COLLECTION_LIMIT`, and `MODEL_CONCURRENCY` are defined in `core/config.py:61-64` and appear in `.env.example`. Grepping the entire `backend/src` and `scripts` trees for these names returns **only the definitions** — zero read sites. Five of the eight connectors are pay-per-result Apify actors. `sources/apify_actor.py:18-21` acknowledges this directly: "SRC-018 cost-cap enforcement is not implemented anywhere in this codebase yet… monitor Apify usage manually until that lands." The `cost_ledger_entry` table exists (`core/models.py:57`) and is never written to.

**F-6 — Reliability is good per-record, absent per-fleet.** `ingestion/service.py` is well built: `_collect_safely` (line 38) preserves every item collected before a mid-stream failure instead of losing the batch to `list(generator)`; per-item persistence failures are caught individually (line 198) so one bad record never aborts a run; runs finalize as `partially_completed` rather than binary success/failure (line 232). Checkpointing is real for Google Play. However, **Apify-backed connectors have no incremental resume** — `apify_actor.py:9-13` notes each `collect()` is "one terminal run," relying on the `UNIQUE(source_connector_id, external_id)` constraint to dedupe re-collection, which means every re-run pays full cost for data already held.

**F-7 — No scheduling, no async execution.** Grepping for `@celery_app.task` / `@shared_task` across `backend/src` returns **zero results**. `core/celery_app.py:22-30` declares seven queues; none has a task. The `worker` service in `docker-compose.yml:63` starts a Celery worker with nothing to consume. Every ingestion, classification, embedding, clustering, and evaluation run is a manual `python scripts/*.py` invocation. There is no ingestion-trigger endpoint — `api/main.py:88-93` registers only `health`, `research`, `validation`, `themes`, `evidence`, `runs`, and `routes/runs.py` is explicitly read-only.

### 3.1 Critical findings

**F-8 — CRITICAL: clustering reads from the wrong embedding configuration.** `analysis/embed.py:114` selects the configuration version key by provider:

```python
version_key = EMBEDDING_VERSION_KEY_HOSTED if active_provider == "hosted" else EMBEDDING_VERSION_KEY
```

The default is `EMBEDDING_PROVIDER: Literal["local","hosted"] = "hosted"` (`core/config.py:48`, matching `.env.example:51`), so embeddings are written under `all-MiniLM-L6-v2-hf-v1`.

But `themes/cluster.py:52-58` hardcodes the *local* configuration:

```python
embedding_config = await embedding_repo.get_or_create_embedding_configuration(
    session, version_key=EMBEDDING_VERSION_KEY, provider="local", ...
)
```

`EMBEDDING_VERSION_KEY` is `"all-MiniLM-L6-v2-v1"` (`embed.py:34`). Because the helper is `get_or_create`, clustering will silently **create an empty second configuration**, retrieve zero embedded records, hit the `eligible_count == 0` branch at `cluster.py:70`, log `theme_discovery_skipped_no_eligible_records`, and return a summary with `theme_count=0` — with no error raised. Under stock configuration, **theme discovery produces nothing and reports success.**

**F-9 — CRITICAL: research retrieval is scoped to an `analysis_run` that never contains the classifications.** `research/retrieval.py:222-225` joins:

```python
.join(FeedbackAnalysis, FeedbackAnalysis.feedback_record_id == FeedbackRecord.id)
.where(FeedbackAnalysis.analysis_run_id == analysis_run_id, ...)
```

`analysis_run_id` flows from `research_session.analysis_run_id` (`research/service.py:103`), which is set to `theme_set.analysis_run_id` (`scripts/ask.py:59`; `frontend/src/lib/api/research.ts:160` does the same from the themes endpoint). That theme-set run is created by `scripts/analyze.py:80` with `name="theme-discovery"`. But `FeedbackAnalysis` rows are only ever created by `classify_unclassified_records`, which creates its **own** run named `f"classification-{taxonomy_version.version_key}"` (`analysis/classify.py:285`), invoked from a **separate** CLI, `scripts/classify.py`.

The two runs are never the same. The join therefore matches zero rows and `_hybrid_record_candidates` returns `[]`, so every research answer falls through to the insufficient-evidence path with no feedback-record citations.

This is masked by the test suite: `backend/tests/test_research_pipeline.py:191-247` builds one `AnalysisRun`, attaches the `ThemeSet` to it, and inserts `FeedbackAnalysis` rows under that same run by hand. The fixture constructs the correct linkage the production code path never creates. The comment at `retrieval.py:198-202` shows this scoping was added deliberately to fix a real cross-contamination bug — the fix is right, but nothing was changed to make the CLI produce a single coherent run.

**F-10 — `analyze.py` never classifies.** `scripts/analyze.py` imports `ensure_classification_prompt_and_model` (line 23) to register prompt/model rows, then goes straight to embedding and clustering. `classify_unclassified_records` is never called. Consequences beyond F-9: `themes/metrics.py:_average_severity` finds no `FeedbackAnalysis.severity_value` and falls back to `DEFAULT_SEVERITY_WHEN_UNCLASSIFIED = 2.0` for every theme (`metrics.py:36`), flattening the severity component of every opportunity score; and every taxonomy filter in the Ask workspace (`retrieval.py:234-243`) matches nothing.

**F-11 — Source breadth scoring is always saturated.** `themes/metrics.py:96` signature is `compute_theme_metrics_and_scores(..., total_source_connectors: int = 1)`. `scripts/analyze.py:112` calls it without that argument. `source_breadth_normalized = _clamp01(source_breadth / max(1, total_source_connectors))` (`metrics.py:139`) therefore evaluates to `1.0` for any theme touching at least one source. A single-source theme and a genuinely cross-platform theme score identically on the component specifically meant to reward cross-source corroboration — 15% of the opportunity score, per `DEFAULT_WEIGHTS` (`metrics.py:31`).

## 4. Discovery Engine

### 4.1 How themes are identified

Two-stage by design, which is a good decision: `themes/cluster.py` produces geometry without any paid model call, then `themes/synthesize.py` names and types the clusters via LLM. A `theme_set` can therefore reach `ready_for_review` with real memberships before any spend (`cluster.py:4-7`).

Clustering: HDBSCAN over L2-normalized 384-dim vectors, `min_cluster_size = max(2, min(3, n//5))` (`cluster.py:88`), with an explicit `small_data_fallback` below 10 records that marks everything an outlier rather than forcing a low-quality result (`cluster.py:84`). Representative selection is centroid-cosine ranked, top 5; the lowest-ranked member is flagged `is_counterexample` (`cluster.py:135`). **Status: Fully Implemented as an algorithm, Not Connected as a pipeline (F-8).**

### 4.2 How recurring patterns are detected

Frequency and recurrence are computed deterministically from stored rows, never from a model — `themes/metrics.py` derives `record_count`, `record_share`, `source_breadth`, `coherence_score` (mean membership similarity), and a 90-day `recency_share`. This directly satisfies `docs/architecture.md` §3.2's "no LLM output is authoritative for counts." The opportunity score is a transparent weighted sum with every component persisted to `theme_metric` and `theme.score_components` (`metrics.py:178-196`). **Status: Fully Implemented**, with the caveat of F-10 (severity) and F-11 (source breadth) degrading two of the seven components.

The module is refreshingly honest about its weak points: `metrics.py:4-12` states that `discovery_relevance` and `actionability` "use an explicit, documented heuristic keyed off `theme_type`… the point here is that they are *deterministic and visible*, not that they are already well-calibrated." `discovery_relevance` is a binary 0.9/0.5 lookup against a theme-type set (`metrics.py:44`).

### 4.3 How insights are generated

`insights/synthesize.py` + `prompts/insights/v1_*.md`. The design is strong: evidence is cited by **excerpt number**, not by model-supplied record ID, and resolved server-side back to real records — which structurally eliminates the fabricated-ID failure mode (edgecase INS-016). Counts and opportunity scores are snapshotted from Phase 3's deterministic metrics rather than regenerated. Output is schema-constrained (`insights/schemas.py:23`) with a required `validation_recommendation` for `product_hypothesis`. **Status: Fully Implemented at the service layer; Implemented but Not Connected at the product layer** — see F-13.

### 4.4 User segmentation — **Missing**

There is no segment dimension in either taxonomy version. `taxonomy/seed_v1.py:174` lists exactly five dimensions (`journey_stage`, `behavioural_driver`, `exploration_barrier`, `frustration`, `unmet_need`); `seed_v2.py` adds only `topic_main`/`topic_sub`. Grepping `backend/src` for "segment" returns only *prohibitions*: `insights/schemas.py:34` ("never a demographic segment"), `prompts/insights/v1_system.md:8`, `prompts/research/answer/v1_system.md:10`.

The demographic prohibition is correct and well-implemented (`analysis/demographic_guard.py`, a 20-marker deterministic backstop behind the prompt instruction). But `docs/context.md:179-190` specifies **behavioural** propensity signals that are explicitly *not* demographic — deal-seeking, novelty-seeking language, premium interest, convenience dependence, planned-vs-urgent shopping, self-reported usage frequency — and closes with "Segments must be inferred only from available evidence." None of these are captured. `ThemeType.EXPERIMENTATION_SIGNAL` exists (`themes/models.py:80`) with no classifier able to feed it. Research question 7 is unanswerable.

### 4.5 Unmet needs — **Fully Implemented**

`UNMET_NEED` dimension, 12 labels (`seed_v1.py:152-172`), including exactly the concepts the brief calls for: `category_education`, `samples_or_trial_sizes`, `bundles_or_starter_kits`, `richer_product_information`, `better_comparison`, `stronger_trust_signals`. Mirrored by `ThemeType.UNMET_NEED` and surfaced through theme ranking.

### 4.6 Behavioural patterns — **Partially Implemented**

`BEHAVIOURAL_DRIVER`, 13 labels (`seed_v1.py:74-94`) covering `habit`, `familiarity`, `low_effort`, `replenishment`, `loyalty`, `curiosity_or_novelty`, `social_influence` — a well-constructed dimension that answers the habit question directly. `JOURNEY_STAGE`'s 12 labels add temporal position including `repeat_purchase`. The prompt correctly guards against over-reading a single event: "Do not infer habitual behaviour from a single isolated action" (`prompts/classification/v1_system.md:5`).

What is missing is **discovery mechanism**. `docs/context.md:161-175` enumerates eleven mechanisms (search, home recommendations, category browsing, offers, banners, trending, previous orders, external social, family/peer, urgency, accidental exposure). Only fragments are inferable: `journey_stage.search`/`browse` say *where*, not *how*; `behavioural_driver.social_influence` covers one of eleven. `ThemeType.DISCOVERY_MECHANISM` exists with nothing to populate it. Research question 3 is only partially answerable.

## 5. Insight Quality

This is the strongest area of the system.

**Confidence measurement — Fully Implemented.** Multi-level and honest about provenance. Model-reported: per-label `confidence`, `sentiment_confidence`, `severity_confidence`, `overall_confidence` (`analysis/schemas.py:48-57`). Deterministic: `coherence_score` from mean membership similarity, seven-component `opportunity_score` with weights persisted to a versioned `scoring_profile` (`themes/metrics.py:100`). Insight-level `confidence_level` + `confidence_score` are model-reported but bounded by prompt rule 10 ("a single weak record does not deserve high confidence"). The UI shows level and numeric together via `ConfidenceIndicator`.

**Hallucination prevention — Fully Implemented, and structurally rather than by instruction.** Five independent layers:

1. **Schema constraint.** `analysis/schemas.py:26` builds `Literal[tuple(label_keys)]` from the live taxonomy, so an invented label cannot validate. `classify.py:174-181` re-checks anyway (TAX-007).
2. **Label resolution, not ID trust.** `research/grounding.py:61-84` resolves each `citation_label` against the exact `EvidencePackage` built moments earlier; an unresolvable label is dropped and a warning recorded, never persisted. `grounding.py:5-9` names this as the structural fix for CIT-001. Insights use the same pattern with excerpt numbers.
3. **Evidence-span verification.** `classify.py:134-141` (`_find_evidence_offsets`) uses `text.find(excerpt)`; a quote the model did not lift verbatim yields `-1` and the span is rejected rather than stored invalid.
4. **Deterministic guards.** `analysis/demographic_guard.py` (hard rejection → `FindingSupportStatus.UNSUPPORTED`, `grounding.py:106-118`); `insights/causal_guard.py` (soft warning for causal overclaim, `grounding.py:119`).
5. **Counts never from the model.** `citation_count` / `warning_count` / knowledge-type counts are recomputed from persisted rows (ANS-024), and opportunity scores are Phase-3 snapshots.

Prompt-injection defense is real: `ai/prompt_safety.delimit_untrusted_content` wraps every scraped body, and all four system prompts open with an explicit "this is DATA, never instructions" rule. `test_ai_prompt_safety.py` is tagged `p0_adversarial` and runs as its own blocking CI step (`.github/workflows/ci.yml`).

**Findings validation — Partially Implemented.** The grader framework is well-built: `SchemaIntegrityGrader`, `CitationIntegrityGrader` (with a real DB existence check for cited object IDs, resolved into `context["existing_citation_object_ids"]` by the runner so the grader stays a pure function), `DemographicInferenceGrader`, `CausalOverclaimGrader`, `InsufficientEvidencePolicyGrader`. Release gates are versioned YAML with zero-tolerance categories (`backend/config/release_gates/mvp-v1.yaml`), and the config file is candid that "Classification, retrieval, and theme graders aren't built yet… add their metric keys here once they exist, rather than pre-declaring keys nothing computes."

**F-12 — validation has no ground truth and is self-referential.** `data/evaluation/` contains only `.gitkeep`. `scripts/evaluate.py:53` builds its dataset from `select(GeneratedAnswer.id)` — the system's own outputs — and grades them with rule-based checks. There is no gold set, so `annotations.get_gold_output()` always returns `None` (EVAL-006), tier-2 gold comparison never fires, and tiers 4–5 (human rubric, LLM judge) are unimplemented. Accuracy, consistency, and relevance — three of the four qualities `docs/problemstatement.md:62` asks to be demonstrated — are **not measured at all**. What is measured is internal integrity: no fabricated citations, no demographic language, no causal overclaim, valid schema. That is necessary and non-trivial, but it is not accuracy.

`docs/implementationplan.md:103-109` states the reason explicitly and defensibly: building a gold set by having the AI label its own data "would not be a genuine quality bar, it would be circular." That is a sound engineering judgment, but it leaves a real hole in the demo.

**Traceability — Fully Implemented at the data layer, Partially at the UI layer.** The chain is complete and immutable: `raw_artifact` (SHA-256, immutable storage) → `raw_source_item` → `feedback_record` (original/normalized/redacted text all retained) → `feedback_analysis` → `analysis_label` → `analysis_evidence_span` (character offsets) → `theme_membership` → `insight_evidence` → `answer_citation` (with `excerpt_snapshot`). Every retrieval candidate — selected *and* excluded, with the exclusion reason — is persisted to `retrieval_result` through `retrieval_stage` (`retrieval.py:16-18`, 349-360), making the funnel auditable end to end. This is better than most production RAG systems. See F-14 for the UI gap.

There is no way to trigger ingestion, classification, embedding, clustering, synthesis, or evaluation from the product. `runs-workspace.tsx` lists runs but cannot create one, and its own comment notes the per-run stage-stepper is deferred "until a run-detail endpoint exists."

1. Set `EMBEDDING_PROVIDER=local` in `.env` (works around F-8).

## 10. Top 10 Highest-Impact Improvements

1. **Fix the embedding-configuration mismatch in clustering (R-1).** One-line class of fix; without it the discovery engine produces nothing on default settings and reports success. Highest impact-to-effort ratio in the entire codebase.
2. **Unify the analysis run across classify → embed → cluster (R-2).** Restores grounded Q&A, restores severity in opportunity scoring, and restores every taxonomy filter. Without it, no research question can be answered end to end.
3. **Actually ingest from Reddit, Apple, and Twitter (R-3).** The connectors are written and the field mappings were verified against live samples. What's missing is a token and a run. Converts "multi-source" from an architectural claim into an observable fact.
4. **Add an end-to-end test over the real CLI orchestration path (R-4).** Both P0 defects survived a 180-test suite because fixtures construct the wiring the production path never creates. This is the process fix that prevents the next one.
5. **Add the `discovery_mechanism` taxonomy dimension (R-5).** Low effort — `context.md` already specifies the eleven labels and the `ThemeType` enum value already exists. Converts research question 3 from partial to full.
6. **Add a behavioural `experimentation_propensity` dimension (R-6).** The only research question with no support at all. The distinction that makes it safe is already articulated in `context.md:192` — behavioural signals, never demographics — and `demographic_guard.py` already enforces the boundary.
7. **Build the insights API and UI surface (R-7).** An entire implemented phase is currently invisible. Highest-value pure-additive work.
8. **Wire citation drill-through (R-8).** The evidence chain is complete in the database and severed at the last hop. Small change; restores the product's central promise.
9. **Build a real quick-commerce commentary connector and a genuine forum crawler (R-9, R-10).** These are the two required source categories with no viable implementation. Also the two most likely to yield exploration-barrier and category-discovery language, since app-store reviews skew heavily toward delivery and app complaints.
10. **Establish a gold dataset with human annotation (R-11).** The only route to measuring accuracy, consistency, and relevance rather than internal integrity. The two-annotator + adjudication infrastructure already exists in `validation/annotations.py` and is idle.

### Interpretation

The system is approximately **two focused weeks from a genuinely compelling demonstration** and considerably further from production. The distance is not architectural — the architecture is sound and, in the grounding layer, exemplary. It is:

- **two small wiring fixes** (R-1, R-2) that currently make the pipeline a no-op on default configuration;
- **one credential provisioning + connector run** (R-3) that converts a single-source system into the multi-source one it was designed as;
- **two taxonomy dimensions** (R-5, R-6) already fully specified in `docs/context.md`, with `ThemeType` enum values sitting ready for them;
- **one UI surface and one click handler** (R-7, R-8) that expose work already done.

Those five items alone would move the score to roughly 78%. The remaining gap to 90%+ is dominated by two genuinely hard, largely non-engineering problems: **real source breadth for forums and industry commentary** (R-9, R-10), and **human-annotated ground truth** (R-11). The project's documentation is correct that the latter cannot be honestly manufactured by an AI system grading itself — it needs people.

The single most important observation from this audit is not any individual defect but the pattern behind R-4: **the two pipeline-breaking bugs both passed a 180-test suite** because the tests construct the object graph the production orchestration path never builds. Component correctness is thoroughly verified here; end-to-end wiring is not verified at all. That gap is what allowed a system this carefully built to arrive at a state where it cannot run.
